# Turning website clicks into reviewed pull requests

No tool available today does everything Apostrophe Software has in mind: open any GitHub project or live site, click text anywhere on the page, type new copy, and send every change as one pull request (a proposed change that a developer reviews before it goes live). Click-and-type editing is now common, but only inside hosted AI builders such as Lovable, Bolt, v0 and Replit, and only for projects that live on those platforms. The tools that work on an existing GitHub project either route the edit through an AI agent (Claude Code desktop, Cursor, Windsurf), work with one framework only (Onlook, small Next.js projects), require the copy to be restructured first (TinaCMS, CloudCannon), or are commercial and aimed at larger teams (Builder Code, formerly Builder.io Fusion). The user's finding about ship.studio was accurate until recently: on **October 21, 2026** Ship Studio added a side-panel "Text" field that rewrites copy in the source without AI, but you still do not type directly on the page. The proposed tool is **feasible as a narrow first version**: editing plain, fixed text on AI-built marketing sites built with plain HTML, Astro or React, and bundling the edits into one change file and one pull request. Making it work for every framework and every kind of text is a much larger, ongoing job. Demand is implied by the size of the AI-coding market and by every major platform shipping its own visual editor, but no direct evidence of demand for this exact workflow was found. That makes a small, open-source first version a sensible way to test demand while building Apostrophe's credibility, rather than a bet on a standalone business.

## Ship Studio now edits text from a side panel, not on the page

Ship Studio is a free, MIT-licensed desktop app for macOS and Windows that previews a local project and works alongside your own AI agent (Claude Code, Codex, Cursor CLI and others). It can open pull requests with AI-written titles and descriptions ([GitHub README](https://github.com/ship-studio/ship-studio)). Its visual editing was mainly about layout and styling until **pull request #1130, merged October 21, 2026**, added a "Text" field to the side panel. You select an element, either in the preview or in an element tree, and type the new copy into that field. The app then rewrites the source file directly, "without interacting with the Preview or with code," and without spending AI credits ([PR #1130](https://github.com/ship-studio/ship-studio/pull/1130)). Only text-focused tags such as headings, paragraphs, buttons and links get this field, and reviewers flagged two open bugs: saves can fail after editing an attribute on the same line, and swapping tags in React or Next.js projects can crash the live reload. The pull request page does not show that either bug was fixed.

So the user's observation was right for any version before late October 2026, and it is still partly right now. The edit happens in a form field, not by typing on the page, and copy that lives in data arrays, translation files or a CMS (content management system) is not covered. Because Ship Studio opens pull requests from the user's working copy, several text edits can in practice go into one pull request, but there is no dedicated "review all my copy changes" queue. **Note:** the ship.studio website and its release notes could not be fetched directly, so it is unconfirmed which public release includes the Text field.

## Click-and-type editing exists, but mostly inside walled platforms

The hosted AI builders have set the pattern non-developers now expect. **Lovable** offers an "Edit text inline" button for typos, headlines and labels without writing a prompt ([Lovable docs: Design](https://docs.lovable.dev/features/design)). **Bolt** lets you double-click text, saves edits in a batch, and applies them together when you click "Save changes" ([Bolt support](https://support.bolt.new/building/visual-edits)). **Replit** applies simple text edits straight to the source without AI credits, though it cannot edit elements made of several parts ([Replit docs](https://docs.replit.com/design/visual-editor)). **v0's** Design Mode can edit text from a panel, but users complained in early 2026 that simple edits now need an "Apply" step, cost credits, and sometimes do not stick ([Vercel community](https://community.vercel.com/t/new-design-mode-why-do-simple-edits-now-require-ai-credits/44083)). All of these work only on projects that live in that platform. Lovable also commits straight to the main branch rather than opening a pull request ([Lovable docs: GitHub](https://docs.lovable.dev/integrations/github)). Lovable's free allowance for inline edits is described inconsistently across its own pages: 100 per user per day with a 2,000-per-workspace cap on one page, and 500 per IP address per day on another ([Lovable docs: Preview toolbar](https://docs.lovable.dev/features/preview-toolbar)). Lovable and Replit documentation could only be read through search-result summaries.

AI coding tools that work on any project take a different route: you point at an element and the AI makes the change. Claude Code desktop (February 2026) lets you "select visual elements in the preview and pass feedback directly to Claude" ([Anthropic blog](https://claude.com/blog/preview-review-and-merge-with-claude-code)). Cursor's visual editor and Windsurf's "Send element" button work the same way ([Cursor blog](https://cursor.com/blog/browser-visual-editor); [Windsurf docs](https://docs.windsurf.com/windsurf/previews)). That is convenient for developers, but each change costs AI usage, can touch more code than intended, and still needs someone comfortable with a coding tool.

Among tools for existing GitHub projects, **Builder Code** (renamed from Builder.io Fusion, reportedly in September 2026) is the closest commercial match. It connects to GitHub, GitLab, Bitbucket or Azure DevOps and "lets anyone on the team create Pull Requests directly to your codebase using a visual editor," and it is explicitly marketed to marketers and product managers ([Builder docs](https://www.builder.io/c/docs/fusion-projects-overview); [Builder for marketers](https://www.builder.io/for/marketers)). One Product Hunt user said an earlier version only edited pages created in Builder ([Product Hunt](https://www.producthunt.com/p/builder-io/fusion-1-0)), and its pricing was not verified. **Onlook** is the leading open-source option (Apache-2.0, about **27,200 GitHub stars**), but it focuses on Next.js with Tailwind and is a full design tool rather than a copy editor ([GitHub](https://github.com/onlook-dev/onlook)). Sources conflict on how it handles text: reviewers say double-clicking edits text, while Onlook's own help says double-clicking jumps to the code ([Onlook help](https://help.onlook.com/en/articles/6-code-editor)). Sources also disagree on whether its changes land in a local copy or in branches and pull requests. Two very small open-source projects come closest in spirit. **Editability** edits text on live Next.js sites and publishes a single commit, not a pull request (seen through a search snippet only, [editability.dev](https://editability.dev/)). **visual-copy-edit** does inline copy editing on Next.js development servers, then commits and pushes ([GitHub](https://github.com/megan-holstein/visual-copy-edit)).

The Git-based CMS world offers mature click-to-edit, but at a price that matters for AI-built sites: the copy has to be moved out of the code first. **TinaCMS** lets editors click fields on a live preview and commits to Git, with pull-request review on its higher "Team Plus" tier ([tina.io/pricing](https://tina.io/pricing); [bestgitbasedcms](https://bestgitbasedcms.com/tools/tinacms)). It works on defined content fields, not on text hard-coded into components. **CloudCannon** needs only a few `data-editable` markers on existing HTML, the lightest retrofit found, but branch-based review requires its Team plan ([vikboyechko review](https://vikboyechko.com/blog/cloudcannon-visual-cms-static-sites/)). Netlify's Visual Editor is closed to new teams ([Netlify docs](https://docs.netlify.com/manage/visual-editor/get-started/manage-visual-editing/)). Form-based tools such as Pages CMS and Decap commit to GitHub but offer no click-on-the-page editing. Pricing figures conflict across sources: Tina's Team tier is listed at $24 or $29 per project per month and Team Plus at $41 or $49, while CloudCannon's Standard plan appears as $49–55 per month in most sources and $125 in one, with branch workflows at $300 or $350 per month ([makerstack](https://makerstack.co/reviews/tinacms-review/); [staticmania](https://staticmania.com/blog/best-cms-for-astro)). Tina, Netlify and Decap pages could not be fetched directly.

## Feasible for plain text, hard to make universal

The core technical problem is working out which line of code produced the text someone clicked. The most reliable proven method is a build-time plugin: a small add-on that runs when the site is compiled and tags each page element with the file and line it came from. A mature, MIT-licensed plugin already does this across most bundlers and frameworks, including React, Next.js, Vue, Svelte and Astro: **code-inspector-plugin** ([GitHub](https://github.com/zh-lx/code-inspector)). Astro's development mode adds similar tags by itself, though one third-party source claims Astro 7 stopped doing so, which could not be verified ([Frontman Astro docs](https://frontman.sh/docs/integrations/astro/)). Older shortcuts that read React's internals stopped working when React 19 removed that information, and the React team declined to restore it ([React issue #29092](https://www.GitHub.com/facebook/react/issues/29092)). This churn is a real maintenance cost.

Once the file is known, the tool must change only the words and nothing else. Standard code-rewriting libraries do this by reading the code into a structured outline, swapping one piece of text, and reprinting only that piece so formatting stays intact ([pkgpulse](https://www.pkgpulse.com/guides/recast-vs-jscodeshift-vs-ts-morph-codemods-code-2026)). When no build is available, for example for a live site, the fallback is to search the project for the old text. That works well when the phrase is unique and fails predictably on repeated phrases such as "Learn more," on sentences split around a name or a bold word, and on text styled to look different from the source, such as all caps. The research proposes a layered approach: use the plugin's file and line where available, then search the code, and pass anything still unresolved to an AI agent. **Claude Code Action**, Anthropic's MIT-licensed GitHub workflow, can take that role and push its fix to the same pull request, where a human reviews it ([GitHub](https://github.com/anthropics/claude-code-action)).

Some kinds of text are easier than they look, and some are harder. Translation files and Markdown pages are among the easiest, because the words sit in plain data files. Text passed into reusable components, lists of features stored as data, and text built from variables ("{count} items") are harder. These are best flagged as "needs a developer" or handed to the AI fallback. Text pulled from a CMS or database is not in the code at all. The tool can at most detect it and tell the user, unless the CMS embeds hidden source markers, as Sanity does ([Sanity docs](https://www.sanity.io/docs/visual-editing/visual-editing-client-stega)). Page titles, meta descriptions and image alt text cannot be clicked on the page and need a side panel. No data was found on what share of typical marketing-site copy is fixed text versus CMS or translation text. That share largely decides how often the tool "just works."

**Verdict:** a first version that reliably handles fixed text in plain HTML, Astro and React (Vite or Next.js) sites is realistic. A version that handles every framework and every text source is not a small project, and the existing open-source attempts each cover only one framework.

## Preview hosting and GitHub access decide cost and trust

There are four ways to show the preview, in rising order of cost. The cheapest is to reuse the preview deployments that Vercel or Netlify already create for each change. That costs nothing, but the precise file-and-line mapping only works if the project adds the plugin once, which the tool could propose through its own first pull request. Next is a desktop app that runs the site's local development server (the program that runs the site on a computer for testing). This has no hosting cost but requires Node.js installed, so it suits agencies more than non-technical editors. Then come cloud sandboxes, temporary cloud computers that build and run the project. They cost about **$0.05 per processor-hour** at providers like E2B, and pricing sources partly conflict ([Fly.io comparison](https://fly.io/learn/ai-sandbox-pricing/)). The research estimates a 30-minute session at a few cents, but installation can take minutes, and many real projects will fail to build without private settings or databases. Finally, StackBlitz's WebContainers, which run the project inside the browser, need a paid commercial licence for for-profit production use, at an unpublished price ([WebContainers](https://webcontainers.io/enterprise), read only through a search summary).

Live-site mode, which shows the public website itself, is easy to display but weak at mapping text back to code. Showing someone else's site inside the tool's own page requires a proxy, a go-between server that strips the site's anti-framing protection. That removes a real security safeguard against clickjacking (tricking users into clicking hidden elements) and needs to be limited to sites the user controls ([BrowserStack](https://www.browserstack.com/guide/frame-ancestors); [CISPA](https://github.com/cispa/framing-control-proxy)). A browser extension avoids this entirely by running on the real page. The research judges it the most robust way to capture live-site edits.

For GitHub, a **GitHub App** is the better choice than personal access tokens. GitHub recommends Apps because they ask only for the permissions they need, are installed per project, and use short-lived tokens ([GitHub docs](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps), read through a search summary). The tool needs only permission to write files and open pull requests. All edits, plus the lightweight change file (for example `.copy-edits/2026-11-09.json`), can go into a single commit and a single pull request with a handful of requests, far below GitHub's limits ([GitHub rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). For public projects the user cannot write to, the tool must first create a fork (a personal copy of the project) and open the pull request from there. How this works with a GitHub App was not verified. Trust is a soft but real barrier: in one Hacker News thread, a commenter refused to grant GitHub permissions to an unknown app ([HN](https://news.ycombinator.com/item?id=47164079)). That argues for open-source code and the narrowest possible permissions.

## The market is large; direct demand is unproven

The surrounding market is very large. Lovable reported crossing **$500M in annualized revenue in mid-2026** (a company claim), with about 8 million users ([Startup Fortune](https://startupfortune.com/lovables-500-million-run-rate-makes-vibe-coding-harder-to-dismiss/); [DemandSage](https://www.demandsage.com/lovable-statistics/)). Cursor passed $2B in run-rate revenue by early 2026 ([Dataconomy](https://dataconomy.com/2026/03/03/cursor-hits-2-billion-in-annual-revenue-as-run-rate-doubles/)), and a January 2026 JetBrains survey found 18% of developers using Claude Code at work ([neuronfeed](https://neuronfeed.com/intelligence/state-of-ai-coding-tools-2026)). Revenue figures come mostly from estimators such as Sacra and differ by month and source. Complaints that AI-built sites "all look and read the same" are widespread ([codemyspec](https://codemyspec.com/blog/vibe-coded-websites-look-the-same); [Indie Hackers](https://www.indiehackers.com/post/what-does-it-mean-to-build-your-product-website-or-landing-page-f0efa5ce28)), and the usual fix is human-written, specific copy, which is exactly what this tool would make easier to get into the code.

Direct demand is weaker. The research found **no Reddit, Hacker News or GitHub threads** explicitly asking for an "edit text visually, then open one pull request" tool. The strongest signals are indirect: Lovable, v0, Cursor and Bolt all built visual editing, and several tiny open-source projects appeared in this niche. Today's workaround is a feedback tool such as Marker.io or BugHerd at roughly **$39–59 per month**, which captures comments and screenshots but still needs a developer to make the change ([G2](https://www.g2.com/products/marker-io/pricing); [BugHerd](https://bugherd.com/cp/marker-alternative)). Agencies handing sites to clients are the most plausible first users. The research found no sources at all on learning and development teams, the founder's own client base.

Competition comes from two directions. Platforms have every reason to keep editing inside their own walls (credits, lock-in), which leaves the "any GitHub project, reviewed by pull request" path open. Builder Code already targets that path commercially, and Ship Studio, being free and open source, could add on-page typing at any time. A native "suggest a copy edit" feature from Anthropic or GitHub would be the most serious threat, but none was found.

On licensing and sustainability, the precedents are instructive. SSW, an Australian consultancy, bought TinaCMS in 2024 because it used the tool for its own client sites, and now runs the hosted version and uses it as marketing ([Tina blog](https://tina.io/blog/Tina-Joins-SSW)). That is the clearest model for Apostrophe. Stagewise, despite YC backing, is shutting its hosted account service at the end of November 2026 ([GitHub](https://github.com/stagewise-io/stagewise)), and Decap slowed to donation-funded maintenance ([Decap](https://decapcms.org/blog/sponsor/)). A permissive **MIT licence** best serves credibility and adoption. The Functional Source License, which blocks competing commercial use for two years before becoming fully open, is worth considering only if a paid hosted version becomes the main business ([Sentry](https://blog.sentry.io/introducing-the-functional-source-license-freedom-without-free-riding)). Code borrowed from Stagewise (AGPL, which requires derived work to stay open under the same terms) would constrain those choices, while Onlook (Apache-2.0) and code-inspector-plugin (MIT) carry no such constraint. Maintainer burnout is the hidden cost: 60% of maintainers in Tidelift's 2024 survey had quit or considered quitting, and 61% maintain alone ([The Register](https://www.theregister.com/2025/02/16/open_source_maintainers_state_of_open/)).

## A first version scoped to fixed text and one pull request

The research's own estimate (a judgement, not a sourced figure) is **roughly 1–3 engineer-months** for a focused first version that reuses existing open-source parts, and **12 or more engineer-months** for a mature product with cloud previews, many frameworks, translation and CMS handling, and rich text. The recommended first version avoids building cloud sandboxes altogether:

- **Frameworks:** plain HTML first, then Astro, then React via Vite or Next.js.
- **Preview:** the site's existing preview or live URL, opened with a browser extension that adds an "edit copy" mode.
- **Precise mapping (optional):** a one-time setup pull request that adds code-inspector-plugin to preview builds.
- **What can be edited:** headings, paragraphs, buttons, links and list items whose text is fixed in the code; page title and meta description from a side panel.
- **Out of scope, but clearly flagged:** CMS text, text built from variables, structural changes to rich text.
- **Change handling:** the app applies matched edits directly; unclear ones are written to the change file and passed to Claude Code Action.
- **Output:** one change file (JSON or Markdown) plus one pull request with a readable before-and-after summary.
- **Access:** a GitHub App with only file-write and pull-request permissions; fork flow for public projects the user cannot write to.
- **Licence:** MIT.

A sensible alternative to weigh first is to contribute an on-page typing mode or a plugin to Ship Studio, which is MIT-licensed and has a plugin kit. That trades ownership and branding for a much smaller workload and an existing user base.

## Open questions and source caveats

- How often do Apostrophe's clients, including L&D teams, need copy changes after handoff, and who makes them today?
- What share of AI-built marketing copy is fixed text versus CMS or translation text?
- Will non-developers install a browser extension and approve a GitHub App?
- Is there a paid hosted version worth building, or is this purely a credibility and lead-generation tool?
- Does the Ship Studio Text field now ship in a public release, and does it support clicking text in the preview?
- What does Builder Code cost today, and does it still struggle with pages not built in Builder?
- Could the "Apostrophe" name cause confusion with ApostropheCMS, an existing open-source CMS? This is unverified; a trademark check is worth doing before naming the tool.

**Sources that could not be fetched directly** (findings rely on search summaries or third parties): ship.studio and its release notes, Lovable and Replit docs, tina.io, Netlify and Decap docs, docs.github.com, webcontainers.io, Sanity docs, Onlook's docs, editability.dev and frontman.sh. **Figures that conflict:** Lovable's free inline-edit limits, Tina and CloudCannon prices, cloud sandbox prices, Onlook's text-editing and delivery behaviour, Pages CMS star counts (2,300–3,300), and the timing of Sveltia CMS 1.0. All effort estimates are researcher judgement.

## Conclusion

The real opportunity is less "a visual editor" than "a safe, reviewable way for the person who owns the words to change them." Every platform has shown that non-developers want to type on the page, yet none has paired that with the pull-request review that keeps developers in control of code they did not write. That framing favours a deliberately modest tool. Edit only what can be changed safely, say plainly what cannot, and let a developer (or an AI agent under review) handle the rest. Over-promising "any site, any text" is the fastest route to the support burden that sinks solo open-source projects.

For Apostrophe, the strongest case is the SSW-TinaCMS pattern rather than a standalone product: a narrow MIT tool that the consultancy uses on its own client handoffs, demonstrates in its work with L&D and marketing teams, and offers setup services around. The cheapest next step is not code but evidence. A handful of conversations with current clients about who edits their site copy, and how, would show within weeks whether this tool is a differentiator worth 1–3 months of building.
